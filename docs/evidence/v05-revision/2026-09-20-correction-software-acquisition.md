# C01：複数年度の原価を、既存の一つのソフトウェア振替へ接続

実施日: 2026-09-20（日本時間）。Issue #20 / 親Issue #19 / PR #18。
基点: `725ed68e2d59aae5efc70ae54c1fc5b5aed12a5c`（少額設備のC02修正を保持）。

## 実装した範囲

残高画面に「複数年度の製作費を、ソフトウェア全体の原価へまとめる」を追加した。既存の制作中残高、年度付き原価リンク、指定された採用版の期首または確認済み外部期首を読み、既知小計と未算定・未組入れを区別する。元の費用資料を既存残高へもう一度足さない。

`softwareAcquisitionDraft.ts` は既存の `balanceUseSources`、`draftBalanceUse`、`traceBalanceLots`、`externalOpeningIssues` を使用する。各対応元の既存振替案を一つの通常のtransferへ結合し、元の原価年・配分ID・出典を保持する。新しい台帳・保存API・承認基盤は作らない。金額の再入力を要求せず、既存の `BalancesPage.edit` から未保存の残高入力へ追加する。この後のブラウザ控え、版付き保存、サーバーの年度採用照合、固定JSON/Markdownは既存経路を利用する。

2025年60,000円＋2026年60,000円について、取得価額候補120,000円→一つの振替→制作中0円・資産120,000円、費用化0円を実際の既存残高・原価エンジンで検査した。元の支払合計と残高を重ねて240,000円にせず、両年度の内訳を保持する。

## 不明・重複・期首を扱う境界

- 既存の原価使用済額を差し引く。既に費用化した原価を新しい製作費へ戻さない。同じ要求の再送で振替を追加せず、要求内容が変われば拒否する。
- 同じソフトの別の制作中残高にも未使用額がある場合は、小計を全体としない。先に既存の振替で対象範囲を整理する。後日付の使用予約も、一部だけを全体額にする前に対応を確認する。
- 未算定の原価、未組入れの配分、振替日より後の期間、欠けた証拠、追跡不能の移動は、既知小計を失わずに全体額をnullとして保留する。通常業務として条件付き算定された費用を制作中へ無理に組み入れない。
- 外部期首は既存の本人確認と出典を利用し、期首に含む過去費用を再加算しない。取得価額不明を確定値にしない。明細を復元できない外部期首は外部出典のまま保持し、架空の年度別配分を生成しない。
- 採用版を参照する期首は、その正確な版ID・年・制作物・制作中という種類・期末額が一致する場合にだけ受け入れる。最新の別版や資産の未償却残高へ代替しない。
- 受入先は同じソフトウェアの未使用・期首0の資産残高。全体取得・改良に対応する既存の確認済み判断を選ぶ。配分1件の判断を、全体の方法選択や取得判断へ自動流用しない。

## 読取りと画面

対象残高の開始年から完了日までを省略せず読み、既存の原価対応が参照する年も含める。並列読取りは4件まで。既存の `readTreatmentProjection` によるdatasetと年の検査を利用し、複数年度読取りの前後でworkspace版を確認する。指定した期首の採用版IDも検査する。追加直前にもdatasetと版を確認し、エラー時は古い読取り結果を使わず、元の残高入力を保持する。

これは複数HTTP呼出しを一つのDB transactionにしたという意味ではない。年度採用時のサーバー側snapshotと版・原価上限・参照検査は維持する。React画面の選択途中の値そのものを新しい永続控えへ保存したわけではない。振替案を既存残高入力へ追加した後は既存の復旧用控えの対象になる。

## 是正計画の残件

C01は原価集約と既存振替まで実装したが、C03の「全体取得価額から選んだ方法→年額→費用化・翌年・訂正」の自動接続は残る。19件の中の2027年24,000円費用化は、既存の汎用費用化へ渡した明示的な合成入力であり、選んだ方法から自動計算した結果ではない。その後の96,000円期末と元原価保持は検査したが、C03完了に読み替えない。

C01の既知小計と除外範囲の画面説明、複数制作中残高の整理支援、原本なしの保存資料出力を含む実API/React総合受入は残る。C02に追加した7件の実schema・共通projection・SQLite統合試験も、この環境では未実行。C04の共通事実再利用と未送信入力復旧、C05の文書検査整理、C06の展示・配布との整合は継続作業とする。
