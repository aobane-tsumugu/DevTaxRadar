# 領収書・請求書のローカル候補抽出

この機能は**未確認の入力候補**を作ります。読み取り結果をそのまま費用へ保存したり、税務上の扱いを決めたりしません。元の支払の共通入力で値と支払の種類を選び、必要な情報を補い、候補確認 → 年度影響確認 → workspace一括保存を行います。年度資料の採用はさらに別操作です。

## 対応範囲

- UTF-8の `.txt`：英語・日本語の明示的な見出しを持つ発行元、請求日、支払日、通貨、合計額、利用期間、請求書番号
- `.pdf`：文字データを持つPDF。複数ページを含むが、文字列の順序・文字の欠落・複雑な表構造によって候補が不足する場合がある
- `.json`：次の厳格な文書フィールド形式。すべて任意の文字列、versionのみ必須。未知項目・重複キー・配列・数値型は拒否する

```json
{
  "version": 1,
  "issuer": "Example Supplies",
  "invoiceNumber": "INV-2026-001",
  "billedOn": "2026-06-01",
  "paidOn": "2026-06-03",
  "currency": "JPY",
  "total": "1000",
  "startedOn": "2026-06-01",
  "endedOn": "2026-06-30"
}
```

これは原始請求v1の `candidates` JSONとは別の形式です。原始請求v1は従来の「構造化CSV・JSONを読み込む」欄を使います。

ラベル例は `Issuer: Example Supplies`、`Invoice Date: 2026-06-01`、`Currency: JPY`、`Total: 1000`。任意事業者の請求レイアウトを完全に解釈する汎用OCRではありません。画像ファイル・スキャンPDF・暗号化PDFは対応せず、手入力へ進めます。壊れた文書や上限超過も費用を変更せず終了します。

## 上限と安全な処理

ファイルは5 MiB、PDFは20ページ、抽出文字はUTF-8で512 KiB、PDFテキスト項目は20,000個、読み取りは15秒以内。テキスト解析は10,000行、1行2,048文字、各項目20候補、候補160文字までです。暗号化PDFのパスワード入力や外部サービスへの転送は行いません。

PDF.jsを同梱のローカルWorkerで実行し、選択したファイルのバイト配列だけを渡します。URLによる文書取得・CDN・外部フォント等の取得・埋め込みJavaScript実行・添付資料展開・リンクへの移動・HTML表示はしません。ファイルシステムのパスをAPIへ渡す処理もありません。Workerは成功・失敗・取り消し・時間切れで破棄します。新しい選択・画面移動・保存版変更・画面を閉じた後の古い結果を適用しません。

数式・HTML等は実行しません。日付の曖昧な順序、通貨記号だけの通貨、負数・読み間違い・不正な桁区切りを推測で確定しません。複数候補がある項目を自動選択しません。税抜/税込・小計/総額・請求/支払の違いは原本で確認してください。返金は既存の返金・調整画面へ入力します。

## 確認、保存、復旧

読み取り候補の選択値と支払の種類は最初は未選択です。照合のチェック後、選んだ値だけを共通入力へ渡します。円額への採用・外貨換算、発生日・取得日・業務利用開始日、実際の契約、配分・資産の扱いは自動入力しません。請求書番号を契約番号へ転記しません。

選択後は共通入力の手入力・不明理由・証拠ID・候補確認・影響確認・保存の経路を使います。発行元と請求書番号は `OriginalChargeCandidate.document` に、本人が確認した短い値だけ保存できます。根拠ファイルの参照先は既存の `EvidenceRecord` 境界で別途登録してください。原文・ファイル名・ローカルパス・画像を通常DTO、控え、年度資料へ自動保存しません。

読み取り途中のファイルと未選択候補はメモリのみです。中断後に続けるにはファイルを選び直してください。共通入力へ渡した後の選択値・追加入力は既存の入力控えで復旧・書き出しできます。控えの復旧だけでは保存しません。取り消しや保存失敗は以前の費用を変更しません。

取込キーは `receipt:` と抽出テキストのSHA-256から作ります。同じ読み取り結果には同じ費用IDを使い、既存の共通入力がキー・確認済み候補hash・訂正元を照合します。再実行を加算しません。同じキーで確認値を変更して新規登録はできず、保存済み支払の訂正として理由を入力します。別ファイルでも同じ抽出テキストになる場合は同じ文書候補として扱うため、別契約・別請求であることを原本で確認し、必要なら独立した手入力を使ってください。逆に抽出結果が異なる複製は別キーになるため、重複候補の確認は必要です。hashは真正性や一意の請求を保証しません。

既存の費用台帳を二重化しません。追加の発行元・請求書番号も候補内容hashに含め、同額訂正を追跡します。既存の採用年度資料・JSON/Markdownは当時の値を保持し、後の訂正で書き換えません。追加情報を知らない旧クライアントによる既存事実の欠落・変更は保存時に拒否されます。旧実行版へのダウングレード運用は未対応です。

## 明示的に未対応

- 画像OCR、外部AI/OCRへの送信、任意の請求書レイアウトの完全な認識
- 暗号化PDF、手書き、画像のみのPDF、ローカルに同梱されない字体に依存する文字の完全再現
- 所得区分・消費税区分・供用日・資産単位・耐用年数・費用処理の自動確定
- 原本保管、法定保存・電子帳簿保存法への適合保証

テストは合成文書・コンポーネント・API・配布パッケージを対象とします。実ブラウザでの視覚確認、Windows実機、すべてのPDF生成製品との互換性は別の確認です。ローカルでのテスト成功は公開・配布・デプロイの完了を意味しません。

## 同梱ライブラリ

PDF処理はPDF.js (`pdfjs-dist` 6.3.289) のローカルlegacyビルドを使用します。現代的な `Uint8Array.toHex` 等がないNode 24やブラウザでも互換コードを含む構成です。ネイティブのmodule Worker・File/ArrayBuffer・ReadableStreamを備えるブラウザが必要で、利用できなければ手入力へ戻します。ブラウザ別の実機適合を保証するものではありません。

PDF.jsのApache 2.0ライセンスと、legacyビルドが同梱するcore-js 3.50.0のMITライセンスを `docs/licenses/` と公開アセットの `licenses/` に含めます。新しい外部サービスやOCRランタイムの設定は不要です。更新時にはlockfile、依存監査、合成PDF・制限・保存境界・配布パッケージを再検証してください。
