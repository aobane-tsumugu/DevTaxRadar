## 目的と背景

DevTaxの目的は、個人開発で何を作るためにいくら使ったか、そのお金を今年と翌年以後にどう扱うかを、事実と根拠をたどって説明できるようにすること。

主対象は、給与所得があり、副業プロダクトの収益化前後にAIサブスク、PC・GPU等へ支出する個人開発者である。これは [既存仕様](../../PRODUCT_SPEC.md) の想定であり、実ユーザー調査による検証済みの市場情報ではない。

定額AI契約では、複数の制作物、新規開発、保守、一般学習、趣味が混在する。請求書だけでは制作物別費用を説明しにくい。支出、完成、実際の利用開始、売上の時期も一致しない。履歴から復元できる情報と本人にしか分からない事実を合わせ、費用との対応を継続して記録する必要がある。

早期準備では、まだ履歴がなくても、これから何を記録すればよいかが分かること。過去整理では、全履歴候補を見て制作物へまとめ、復元できた事実と分からない部分を区別できること。翌月・翌年には、以前採用した資料を保ち、変更部分だけ見直せること。この3つを一続きの利用体験にする。

収益が少ないことだけを理由に資産化を促さない。金額境界に合わせた支出、形式的な資産分割、実態と異なる供用日変更を提案しない。税額・電子申告・所得区分の自動確定は既存仕様上の対象外を維持する。

国税庁の所得税基本通達49－8の2は、自己製作ソフトウェアに関する合理的な方法による継続的な原価集計・配賦を扱う。このことから、方法の説明と継続性を設計上重視する。ただし、DevTaxのトークン重みが税務上承認されていることを意味しない。[国税庁の該当通達](https://www.nta.go.jp/law/tsutatsu/kihon/shotoku/08/06.htm)

帳簿・請求書・領収書等の保存と、DevTaxの集計結果の保存も区別する。数値snapshotの保存だけで原本保存を代替したとは扱わない。[国税庁の記帳・保存案内](https://www.nta.go.jp/taxes/shiraberu/shinkoku/kojin_jigyo/index.htm)

## あるべき完成像

開発を続ければ、その実態に沿って費用・判断・根拠が積み上がり、今年の扱いと翌年への引継ぎが分かる製品にする。

利用者は、作っているもの、支出、誰が何に使ったか、起きた出来事を確認する。DevTaxは、必要な記録を事前に知らせ、集められる事実を集め、費用を合理的に対応付け、事実と適用条件がそろう範囲の処理候補・金額・残高を計算する。欠けた情報と専門判断が必要な論点を具体化し、採用した内容を次年度へ引き継ぐ。

記録を保存することは必要条件であり、到達点の全部ではない。利用者が「この開発費はどこへ行ったか」「なぜ今年はこの扱いになるか」「翌年へ何を引き継ぐか」「次に何を確かめるか」に答えられるところまでを製品の責任とする。

画面の中心となる問いは、何を作っているか、何に使ったか、今年どう扱うか、何を引き継ぐか、の4つ。制作物の生涯と年度別の費用・残高を中心に置き、入力、計算、判断、採用、出力を一貫させる。

## 開発の全期間を支える

| 利用場面 | 完成形で成立すべきこと |
| --- | --- |
| 構想・趣味・事業化の検討 | 履歴なしでも用途と段階に合う記録対象が分かる。支出や出来事が起きた時点で迷わず追加できる |
| 過去の復元 | 全履歴候補、請求、公開物、メモから復元し、事実発生日と復元日、根拠と未知状態を分ける |
| 開発・評価 | 新しい支払と活動を既存の対応へつなぎ、複数制作物の費用と制作中原価を継続して追える |
| 自己利用・外部提供 | 実際の用途と利用開始を確認し、その事実に対応する処理候補と残高移動を計算する |
| 保守・改良・転用 | 稼働中の対象と開発中の改良計画を併存させ、通常費用候補と改良原価候補を実態に沿って分ける |
| 開発中止・廃止・承継 | やめた範囲、残る効用、転用を記録し、残高の扱いと未確認条件を示す |
| 年度の締めと翌年 | 当年費用候補、制作中原価、資産等、前払等の増減を照合し、採用期末を翌期首へ引き継ぐ |
| 相談・訂正・利用終了 | 回答と訂正を同じ対象へ反映し、元版を保持する。アプリを使わなくなっても資料と根拠を読める |

これらは一本道の必須ウィザードではない。旧版を利用しながら改良版を開発し、一部だけを外部へ提供する状態も成立する。制作物、効用や改良の単位候補、用途別の利用状態、出来事、対象期間を分ける。

## お金がどう移るかを最後まで扱う

支払・契約・購入 → 対象期間の費用基礎 → 制作物・活動への対応 → 処理候補と方法の採用 → 当年費用候補・種類別の期末残高 → 翌期首、を追跡する。

- 原額は一度だけ登録する。直接の根拠がある費用は直接対応し、共通費だけを合理的な方法で配賦する。
- AI利用量は、実契約と対象期間の中で費用を対応付ける基準の一つ。業務実態や支払額の代わりにしない。
- 設備の購入額、当年償却等の費用基礎、制作物原価への組入れは別の段階。出典IDで結び、同じ額の二重費用化を防ぐ。
- 制作中原価、完成後の資産等、前払等は種類別の残高を持つ。未判断額は自動的に将来残高としない。
- 残高種類ごとに「期首＋増加＋振替受入−振替払出−費用化−その他減少＝期末」を照合する。支払額と当年費用を同一視しない。
- 完成、利用開始、改良、中止、廃止、承継等による移動は、事実と採用した扱いに結び付ける。
- 同じ確認済み事実で適用可能な方法が複数ある場合、条件、継続性、各年の費用と残高の差を比較できる。異なる事実を仮定した試算は採用版から分離する。
- 税額算定をしない範囲でも、費用候補と残高の比較は製品責務に含める。税額未計算の差を節税額とは表示しない。
- 各処理群について根拠・適用時点・条件・計算を検証する。未対応の処理は対象、理由、影響金額を明示する。

## 判断と自動化の責任分担

| 状態・仕事 | DevTaxの責任 | 利用者・接続先の責任 |
| --- | --- | --- |
| 抽出・照合・計算・繰越し | 取込、重複候補検出、期間対応、配賦、残高増減、整合検査、資料生成 | 読取範囲と支払・事実の正しさを確認 |
| 用途・開始・中止等 | 必要な問いと根拠候補を示し、履歴による推測と本人確認を分離 | 実際の使い方と出来事を確認 |
| 事実と条件がそろう | 処理候補と算定額、根拠を提示。自動的にすべてを要相談にしない | 採用する扱いを確認 |
| 一部の事実が欠ける | 必要な理由、影響金額・期間、回答による違いを示す。他の計算可能部分は進める | 回答、保留理由、確認先を記録 |
| 方法が複数ある | 適用条件と各年の費用・残高の違いを比較 | 適用条件を確認し、方法を選ぶ |
| 専門解釈・未対応・矛盾 | 論点を絞り、資料と質問を作る。回答を同じ対象へ取り込める | 必要な対象について専門家等へ確認し、回答と採用理由を記録 |
| 年度確認・会計への引継ぎ | 費用候補、残高、未判断を照合し、転記元付きの資料・構造化データを作る | 採用版を確認。税額算定・申告は会計ソフトや専門家等の接続先で行う |
| 更新・復旧・持ち出し | 自動保存、競合検出、バックアップ・復元、旧版の読取り、差分、出力時のデータ境界 | 共有権限と外部へ渡す範囲を決める |

言語モデルを用いる場合も、資料整理や質問・説明の補助に位置付ける。事実、円額、税務結論の唯一の根拠にしない。日常の作業は変更箇所の確認で済み、専門用語は必要な判断と結び付けて説明する。

## 現行実装との隔たり

現行の問題と根拠:

| 問題 | 根拠 | 改善する理由 |
| --- | --- | --- |
| 全費用の税務処理生成と原価追跡が未完了 | 共通costProjection、残高増加額との対応、採用版への固定を接続。明示内訳・一意に定まる原価の減少後追跡と前年採用原価の期首照合も接続。全処理の自動生成、初回期首の外部原価、曖昧な内訳の解消は残る | 原額と配分から、当年費用・翌年残高まで説明をつなぐ必要がある |
| 年次処理と全画面の年範囲が未統一 | 概要は対象年の全費用とAI内訳へ修正。API・根拠画面・初期設定結果は全期間の経路を保持 | 対象年の費用・採用残高・根拠を一貫させる必要がある |
| 画面分類と詳細税務coreが未接続 | `classificationView`, `src/core/taxDecision.ts` | 分類ラベルと必要事実の確認が切り離される |
| 観測品質の固定が未完了 | 年度採用版は入力・数値観測・結果を保持し、再走査と分離済み。全契約の捕捉状態とAdapter版は未完了 | 再走査や履歴消失で以前の説明を再現できなくなる |
| 相談回答の個別項目・原因別影響が未完了 | 回答保存・判断確認・見直し導線・固定出力は接続済み。個別設備/契約等との恒久対応と原因別の金額・後年度影響が未完了 | 採用記録・訂正・相談回答まで一貫した資料にする必要がある |
| 未取得状態の契約・期間別管理が不足 | 割合不明と0を分離し、readinessの一律表示は撤去。該当なし・保留・不一致は年度別に保存済み。捕捉外率は全体1値 | 推定を事実のように見せ、不要な入力を促しうる |

React、Fastify、SQLite、ローカル処理、source別増分走査、全候補の番号統合、金額保存則は活かす。全アプリの書換え、マイクロサービス化、クラウド化、LLM追加は必要条件ではない。

## 利用者の流れ

流れの各工程は「利用者が得る答え → 実行する処理と主体 → 分岐・戻り先 → 保存する根拠 → 現在の接続範囲」で設計する。[HTMLのR2](./workflow-blueprint.html#target-flow)に11工程の対応表と制御フローを掲載した。これは実装の着手順ではなく、完成形で同時に成立すべき責務の定義である。

観測候補と本人確認、入力不正と事実不明、計算可能な範囲と未対応の範囲を分ける。不正・競合は入力を保持して修正・比較へ戻り、事実不足は対象・期間・影響を示した質問へ戻る。回答は同じ対象へ反映する。年次照合の不一致は採用を止め、整合した内容は本人確認後に版として固定する。相談資料はその固定版から生成し、新しい事実や翌年度は元版を保持した作業版へつなぐ。

設計変更の評価軸は、原額と活動を説明できること、判断できる範囲が増えること、当年と翌年の接続が保たれること、同じ資料を再入力なしで再現できることである。工程を追加しても、このいずれにも貢献しないなら必要性を見直す。

### 完成形を横断して確認する

HTMLのP2では、次の6つの問いを工程横断の完成条件へ対応付ける。各条件は実装の順番を表さず、対象の制作物・年・版を一致させて成立させる。

| 問い | 完成条件 | 主な受入シナリオ |
| --- | --- | --- |
| この開発費はどこへ行ったか | 期末残高から支払原額へ戻れる。配分後だけでなく、費用化・振替後も同じ原価の重複使用を検出する | AC-GRAPH、AC-YEAR |
| なぜこの扱いになるか | 出来事、本人確認済み事実、適用条件、計算と採用理由がつながる。同じ事実での方法の違いを説明できる | AC-FACT、AC-DECISION、AC-METHOD |
| 分からないものは何か | 不足の対象・期間・影響と質問が結び付き、回答が同じ対象の再確認へ戻る。不明を0や残高へ置換しない | AC-FACT、AC-CAPTURE、AC-CONSULT |
| 翌年へ何を引き継ぐか | 採用期末と翌期首を接続し、前年訂正の影響と未反映を示す。未判断事項は金額残高と分ける | AC-YEAR、AC-CORRECTION |
| 後から同じ説明ができるか | 名前・料金・履歴の変更後にも元版を読める。画面・出力・復元が同じ固定資料を使い、未収録情報を現在値で補わない | AC-RECORD、AC-EXPORT、AC-RESTORE |
| 開発を続けながら使えるか | 稼働版と改良開発を併存させ、変更範囲の確認と中断後の復旧で作業を続けられる | AC-LIFE、AC-SAVE、AC-UX |

各工程の試験成功だけでは、この横断条件を達成したとしない。接続されていない経路は要件対応表で残し、画面の表示もその到達範囲に合わせる。

保存資料の可読性も再現の一部とする。設備の年度配分は当該資料に固定された設備名・制作物名とIDを併記し、名称未収録ならその状態を示す。改名後の現在値で旧版の説明を補わない。この表示を採用前の確認、保存版閲覧、保存版Markdownへ接続した。

1. 早期準備は制作物と用途から、過去整理は全履歴候補から開始する。
2. フォルダのグループと、税務上の単位候補を区別する。
3. 支払原額を一度だけ登録し、対象期間、制作物、用途、証拠を結び付ける。
4. 計算結果を確認し、判断や金額が変わる不足事実だけを埋める。
5. 不明・該当なし・保留理由を正常な状態として保存できる。
6. 内容を確認して採用版を保存する。税務上の最終確定とは区別する。
7. 同じ採用版から相談資料を出す。
8. 翌月や供用・改良等の出来事では差分だけ確認し、訂正版を採用する。

「雑所得／白色／青色」の同額カードは、追加で必要な要件の比較へ変更する。税額差を算定していないのに、金額の比較として見せない。

## 計算とデータの接続

新しいapplication serviceが、期間帰属 → 費用基礎 → 配賦 → 単位集計 → 処理候補 → 共通projectionを作る。画面、採用記録、exportは同じprojectionを使う。

| 概念 | 責務 |
| --- | --- |
| SubscriptionContract | providerとは別に実契約を識別し、sourceの利用を対応付ける。通常はproviderごと1契約を既定生成 |
| ExpenseSource | 1請求・1購入の原額、支払・利用期間、証拠。返金や訂正は元IDを参照 |
| CostBasis | 対象期間へ適用する費用基礎。設備購入額と償却候補を分け、未算定はnullと理由 |
| AllocationPolicyRevision | 契約・期間、方法、重み、timezone、業務率、未取得状態、根拠と版 |
| CostContribution | 費用基礎ID、制作物、活動区分、期間、金額、配賦根拠。原額対寄与は1対多 |
| TaxUnitCandidate / ActivityFact | 単位の境界、用途、直接対応、実際の節目。フォルダのIDとは別 |
| DecisionCandidate | 適用事実、rule/version/日付、条件、不足情報、金額の算定可否 |
| PeriodProjection | 対象期間の原額・基礎・配賦・候補・未算定を共通の出力契約で返す |
| BalanceAccount / BalanceMovement | 制作中原価・資産等・前払等の種類別残高。移動元・先、寄与、理由、対象日、採用版を持ち、期首から期末の増減を追う |
| AnnualReview / MethodScenario | 対象年の費用候補・残高増減・未判断と前年の採用版への接続。条件付き比較と採用済みの扱いを分離 |

費用源ごとの寄与合計を検査し、同じ原額を制作物ごとに複製して二重計上する入力モデルを避ける。設備購入額、年額償却候補、制作物原価累積、当年処理額、将来残高は意味が違うため別フィールドとする。

詳細coreを無検証で接続しない。取得日と供用日、適用期限、用途や所得区分、不足要件の入力契約を検証する。対応する処理は当年費用・残高・条件・例外の保留まで製品として接続し、未対応の範囲を明示する。

## 不明な利用と時間精度

- 観測済み、古いsnapshot、本人推定、割合も不明、を区別する。
- 共有元が切断していても旧寄与がある期間は、全部を未取得として二重留保しない。
- 未取得割合が不明なら、暗黙の10%や25%で採用を完了しない。必要な仮計算は別枠で表示する。
- sourceの複製候補を検出しても、異なる実契約を同じnative IDだけで除去しない。
- 月や用途変更をまたぐ履歴は、取得可能な時間粒度でのみ分割する。精度不足を隠さない。
- トークンのcache/reasoningが包含か独立か等、Providerごとの定義を検証し、その方法版を記録する。

## 記録を保持する方式

観測cache、編集可能なdraft、採用済みReviewRevision、訂正版CorrectionRevisionを分ける。

ReviewRevisionには、入力、正規化した観測寄与、採用方法、engine版、結果、未解決事項、採用日時等を保存する。履歴本文を保存するものではない。元ファイルが消えた場合は参照不可を表示するが、既に採用した数値資料へ削除を伝播させない。

全体をイベントソーシングにする必要はない。現在の編集テーブルとcacheを維持し、採用版と訂正版のsnapshotをSQLiteへ追加する。古いタブの保存を防ぐためexpectedRevisionを照合する。

## 更新・移行でも守るべき契約

- 旧方式の意味、対象年、費用範囲、未知状態、出典を継承する。
- 検証済みバックアップから復元でき、移行失敗で以前の資料を失わない。
- 古い仮定や推定を自動的に本人確認済みへ変えない。
- 計算方式の変更は理由と差額を示し、意図した変更と回帰を区別する。
- 複数制作物・複数年度で、費用から候補、採用、繰越し、出力、訂正、再表示まで一貫する。
- 利用者が差分を確認して方式を採用する。旧資料を保持し、過去の採用版を上書きしない。

## 完成形を判断する条件

全期間の支援、全費用の対応、事実に基づく候補計算、年をまたぐ残高接続、必要な判断の具体化、日常の負担軽減、将来と外部への引継ぎが同時に成立すること。機能を個別に実装しただけでは目的の達成としない。

少なくとも、複数制作物・複数契約、稼働版と改良計画の併存、月境界と年越し、開発中止・廃止・承継、過年度訂正、ルール更新、ログ消失、相談回答の反映、復元と利用終了時の持ち出しを含む経路で検証する。

## 配賦の保存則を確認する合成例

以下は単月の局所検証であり、完成形全体の証明とは区別する。

合成例: AI8,000円、設備の対象期間費用基礎12,000円、自宅費用10,000円、直接費3,000円。

| 費用源 | 制作物A | 制作物B | 私用 | 未取得・未配賦 |
| --- | ---: | ---: | ---: | ---: |
| AI: 未取得10%、捕捉内A50%/B25%/私用25% | 3,600 | 1,800 | 1,800 | 800 |
| 設備: 業務75%、業務分のAは2/3 | 6,000 | 0 | 3,000 | 3,000 |
| 自宅: 業務50%、業務分のAは60% | 3,000 | 0 | 5,000 | 2,000 |
| 直接費: Aへ直接対応 | 3,000 | 0 | 0 | 0 |
| 合計 | 15,600 | 1,800 | 9,800 | 5,800 |

全寄与は33,000円。設備購入額を再加算しない。Aの供用等が不明なら、対応原価15,600円は示せても今年の処理額は未算定とする。

- 15,600円から各費用源、対象期間、割合、証拠、方法へ戻れる。
- 同一revisionの画面・Markdown・JSONが一致する。
- 履歴消失後の再走査で採用済み金額が変わらない。
- 訂正版を作っても元版、理由、差額が残る。
- 前年費用を当年に混ぜず、nullと0を区別する。
- 1費用源の寄与合計超過を拒否する。
- 履歴0件や該当する設備・自宅費用なしでも準備できる。
- 共有切断、複製、月境界、保存競合、途中失敗を含めて確認する。
- 原本本文・パスの境界を維持する。
- 合成fixture・一時DBで計算と移行を検証し、Windows上の保存・復元とlocal APIを確認する。

### 起動条件と自動化の境界

HTMLのR2には、利用開始、履歴取込、支払等の変更、開発の節目、年度採用、相談回答・訂正、翌年開始、閲覧・出力・復元の起動条件を示す。各条件に実行主体、自動で進む範囲、判断待ち・失敗時の戻り先、保存される結果を対応付ける。これは完成形の責務であり、全経路の実装済み・定期実行済みを意味しない。

計算と作業入力の保存は、年度資料の採用から区別する。計算可能な別項目は進め、不足事項は対象を限定して質問する。本人確認後の採用では版・hash・前年接続・原価重複を再照合する。訂正や相談回答は同じ対象へ戻し、元版を保持して影響年を示す。閲覧や年の選択だけで採用版を書き換えない。再送・中断後の再開でも二重計上せず、同じ入力と方法版から同じ説明へ戻れることを自動化の完成条件とする。
