P1

なぜDevTaxを作るのか

開発に使ったお金と実際の活動を、後から説明できる原価の記録にする。

製品の目的

何を作るために、いくら使ったか。
そのお金を今年と翌年以後にどう扱うか。
事実と根拠をたどって説明できるようにする。

収益化前から支出する個人開発者が、AI料金、設備、自宅費用、直接費を、制作物・改良計画と実際の開発段階へ結び付ける。開発初期には「これから残す記録」を知り、過去の整理では「復元できた事実と分からない部分」を区別する。税務処理の候補を確認し、翌月・翌年や相談相手へ引き継げる状態まで支援する。

背景・対象既存仕様から確認できること設計への帰結
主な利用者給与所得があり、副業プロダクトをこれから収益化したい個人開発者。売上ゼロ・少額の段階でもAIサブスクやPC・GPU等へ支出する。帳簿や税務の専門用語を理解していることを開始条件にしない。所得区分を未判定のまま記録を始められる。
定額AIの難しさ1つの契約で複数の制作物、新規開発、保守、調査、趣味が混ざる。請求書だけでは制作物別金額が分からない。請求額と利用履歴を別に持ち、合理的な方法で結ぶ。トークン数を実際の支払額と呼ばない。
収益と費用の時間差先行支出が発生し、実際に使い始める時期や売上の時期は後になる。後から処理を検討するための材料が必要。売上が少ないという理由だけで資産化しない。支出の対応先、作業実態、利用開始、制度要件を別々に確認する。
初期と事後の両方早い段階で記録方法を知りたい人と、既にある履歴から整理を始める人がいる。履歴がまだない人も利用開始できる。過去整理では全履歴候補を入口にする現在の方針を維持する。
開発の節目が重要自己利用開始、外部公開、販売、保守、改良、旧版終了、開発中止は別の出来事。1つの公開日だけで状態を決めず、実際の事実発生日と記録日を残す。
相談までの負担税理士等へ、何を作り、何に支払い、どう按分し、何が未確認かを説明しづらい。利用者が別の表を作り直さず、制作物別の費用・根拠・質問を一緒に出せることを完成条件にする。
継続の必要月が変わり、履歴形式や設定、使うPC、開発状況も変わる。毎回全入力を要求しない。新規・変更・未確認だけを確認し、以前採用した記録は残す。

目的の正本：PRODUCT_SPEC.md:11 PRODUCT_SPEC.md:30 PRODUCT_SPEC.md:40 PRODUCT_SPEC.md:76

作り手の事情と、利用者の目的を分ける。 READMEによると起点は3時間のハッカソンで、現在も継続しているOSS。スキャン件数や境界チャートはデモの見せ場になりやすいが、実利用で必要なのは「翌年にも同じ金額を説明できる記録」。想定利用者像は既存仕様に基づくもので、市場調査や実ユーザー実測で検証済みとはしていない。

目的を支える外部の前提

国税庁の所得税基本通達49－8の2は、自己製作ソフトウェアについて製作費用等を集計することに加え、合理的な方法による継続的な原価集計・配賦を扱っている。したがって、DevTaxの設計では計算方法の説明と継続性を重視する。ただし、この記述からDevTaxのトークン重みが税務上認められると結論付けることはできない。国税庁：減価償却資産の取得価額

記帳・書類保存の案内では、帳簿と請求書・領収書等を整理して保存する必要性が示されている。このため、集計グラフだけを帳簿・原本保存の代わりにしない設計にする。国税庁：個人事業者の記帳・帳簿等の保存

P2

何ができたら「役に立った」と言えるか

実装の数や入力達成率ではなく、利用者が持ち帰れる成果で評価する。

利用場面持ち帰れる成果受入条件／目的から外れる指標
開発を始めたばかり作るもの、利用形態、これから残す費用・節目・証拠が分かる。履歴0件でも準備を完了できる。全員に設備・自宅費用を入力させて100%にすることは目標にしない。
過去を整理する全候補の対応先、対象期間の請求、復元した出来事、未取得部分が分かる。税用語を先に選ばず、数件の候補を1制作物にまとめて費用資料を作れる。
毎月の継続前回から変わった支払・用途・節目・未取得状態だけを確認できる。変更なしの情報は再入力不要。速いスキャンだけでなく、利用者が判断し直す負担が減る。
使い始めた／改良した事実の記録によって、どの期間・原価候補の見直しが必要か分かる。公開日＝供用日、Gitの版＝資産単位という自動確定をしない。
相談・年度の整理制作物別の原価資料、対象年の集計、採用方法、不足事実が1組で出力される。画面・出力・採用版の数字が一致し、原額まで戻れる。税額や資産計上額を大きくすることを成功指標にしない。
個々の資料が成立する条件：「この制作物の、この期間の費用」を選ぶと、支払原額・配賦方法・業務との関係・利用開始等の事実・候補・未確認事項が同じ資料にそろい、その採用版を翌年にも再表示できる。製品全体の完成像はP3〜P6に示す、全期間・全費用・判断・年度接続までを含む。

目的を満たしたと判断するための横断条件

以下は実装順ではなく、完成形を評価する条件。工程単体の成功だけでなく、同じ制作物・対象年・資料版を通して答えがつながることを求める。実装済み範囲の判定は要件対応表と検証証跡で行う。

利用者の問い最後までつながる経路成立を確認する操作未達になる具体例受入への対応
この開発費はどこへ行ったか原資料 → 支払原額 → 対象期間の基礎 → 配分先 → 採用した扱い → 当年費用・残高一つの期末残高から元の支払へ戻り、同じ原額が別経路で重複使用されていないことを確認する。制作物別合計が出ても、費用化・振替後の原価に戻れない。AC-GRAPH / AC-YEAR
なぜこの扱いになるか実際の出来事 → 本人確認済み事実 → 適用条件・方法 → 計算 → 採用理由同じ事実で選べる方法と選べない理由を示し、変更時には影響する年と額を確認する。分類ラベルだけが変わり、必要条件や年次計算につながらない。AC-FACT / AC-DECISION / AC-METHOD
分からないものは何か欠けた事実 → 対象・期間・影響 → 質問 → 回答 → 再計算・再確認一項目を未確認に戻す。該当部分は未算定とし、他の算定可能部分を維持する。回答後に同じ対象へ戻る。空欄が0円になる。不明額を将来残高へ回す。資料を出した後の回答が別メモに孤立する。AC-FACT / AC-CAPTURE / AC-CONSULT
翌年へ何を引き継ぐか採用期末 → 翌期首 → 当年増減 → 期末。未判断事項は金額残高と別に継続前年を訂正し、翌年への影響が表示され、未反映の状態を見分けられることを確認する。最新入力で旧版を書き換える。前年との不一致を隠したまま翌年を採用できる。AC-YEAR / AC-CORRECTION
後から同じ説明ができるか採用時の事実・観測・方法・結果 → 固定版ID → 閲覧・出力・復元採用後に名前・料金・履歴を変更し、元版の説明を読み直す。旧版にない情報は未収録と表示する。金額だけ固定して説明を最新入力で補う。画面と持ち出した資料が別の版になる。AC-RECORD / AC-EXPORT / AC-RESTORE
開発を続けながら使えるか出来事を記録 → 変更範囲を確認 → 保存 → 中断・再開 → 次の出来事旧版を使いつつ改良を開発し、月をまたぎ、保存失敗から入力を復旧して続ける。全項目の再入力や、稼働版と改良版のどちらか一方への状態変更を毎回要求する。AC-LIFE / AC-SAVE / AC-UX
設計を採る基準：新機能は上の経路のどこを成立させるかを明示する。スキャン高速化・入力件数・図の数だけでは完成判定を更新しない。未接続箇所を「確認済み」と見せる表示は、計算結果が正しくても修正対象とする。

P3

DevTaxは最終的にどうあるべきか

開発の実態とお金の扱いが、年をまたいでも一続きに分かる製品。

完成像 / 製品仕様v0.5の採用設計

開発を続ければ、その実態に沿って
費用・判断・根拠が積み上がり、
今年の扱いと翌年への引継ぎが分かる。

利用者が税務の分類表を自力で組み立てなくても、作っているもの、支出、実際の使い方、起きた出来事を確認することで、合理的な費用配分と処理候補へ到達できる。DevTaxは必要な記録を事前に知らせ、集められる事実を集め、計算できるところまで計算し、残る判断を具体化する。採用した扱いは年をまたいで引き継ぎ、後から説明・訂正・持ち出しできる。

記録を残すことは必要条件であり、到達点の全部ではない。利用者が「この開発費はどこへ行ったか」「なぜ今年の扱いがこうなるか」「来年へ何を引き継ぐか」「次に何の事実を確かめるか」に答えられるところまでを製品の責任範囲とする。以下は実装の優先順位ではなく、完成形が同時に満たすべき条件。
利用者が知りたいことDevTaxが完成形で返す答え答えの成立条件
今の開発で何を残せばよいか制作物の用途・段階に応じた、支払、利用開始、改良等の記録対象。期限や出来事に結び付いた次の行動。履歴0件でも成立。固定の90日計画を全員へ配らず、記録が必要になる理由と時点を示す。
どれだけ何に使ったか支払総額と、そのうち各制作物・通常業務・私用・未配分へ対応した費用を照合できる。請求額・観測利用量・配賦基準・費用額を別に持つ。履歴は根拠の一つであり唯一の入口にしない。
今年どう扱えるか事実と適用条件に照らした処理候補、その算定可能額、条件、採用した方法を示す。自動的に全件を要相談に逃がさず、根拠がそろう範囲は計算する。未判断分は別に示す。
翌年に何が残るか制作中の原価、採用した資産等の残高、翌期へ回る支払に関する残高を性質別に示す。単なる「今年使わない額」の箱にしない。残る理由と、その後に費用化・移転・終了する条件を示す。
事実や選択が違うと何が変わるか確認済みの同じ事実で適用可能な方法を条件付きで比較。異なる事実を仮定した試算は別表示。税額を計算しない範囲でも、各年の費用候補・残高・必要条件は比較できる。都合のよい事実を生成しない。
相談・申告準備で何を渡すか制作物、年次集計、残高の動き、根拠明細、採用方法、未解決の質問がつながった一組の資料。画面と出力で数字が一致。会計への転記元を示す。申告書の提出や納税額算定は責任範囲から外す。
訂正や翌年の作業はどう続けるか以前の採用版を保持し、新事実・新請求・ルール更新の影響と訂正差分だけを確認する。年次の締めと持越し、過年度訂正、バックアップ・復元、製品を使わなくなった後の読取りまで成立する。

製品の中心に置く4つの問い

何を作っているか / 何に使ったか / 今年どう扱うか / 何を引き継ぐか。ホーム、制作物画面、年次画面、相談資料はこの4つの問いへの異なる入口にする。収集状況・API・トークン・準備スコアを、利用者が最初に理解すべき主題にしない。

P4

開発の全期間を扱う

早期準備、事後整理、日常の更新、利用開始、改良、終了、年度の締めまでを同じ記録でつなぐ。

場面利用者がすることシステムが行うこと到達すべき状態
早期準備作るもの、使う相手、今の段階を伝える。必要な証拠・支払の記録・節目を具体化。該当しない費用入力は省く。記録すべきことが分かり、支出や出来事が起きたら迷わず追加できる。
過去の復元全候補を整理し、請求・公開物・メモ等を補う。復元した日と事実発生日、根拠の強さ、欠けた期間を分離して保存。欠けたログを架空の活動で埋めず、分かる範囲で過去資料を作れる。
日常・月次新しい支払、用途の変化、必要な確認だけ行う。既存の対応を継承して差分を集計。取り込み漏れ・重複候補・方法変更の影響を示す。変わらない情報の再入力なしで、複数制作物・複数契約を継続管理できる。
利用開始・公開誰が何のために、いつ使い始めたかを確認。自己利用と外部提供を分けて該当する候補と残高の動きを再計算。公開日1つから一律に決めず、採用する扱いと理由が残る。
保守・改良・転用既存機能の維持、独立した効用、変更した用途等を記録。稼働している対象と開発中の改良を併存管理し、共通費を一度だけ配賦。同じ制作物内で通常費用候補と改良原価候補が混在しても説明できる。
開発中止・廃止実際にやめた範囲、日付、転用や残る効用を記録。残高の処理候補を提示し、条件不足なら影響残高と質問を示す。中止を全額即時費用化と決めず、対象と未判断額が分かる。
年度確認・翌年当年の対象範囲と採用する扱いを確認。費用候補・残高増減・未判断を照合し、採用期末を翌期首へ渡す。翌年に費用の来歴を作り直さず、対象年度を切り替えて追跡できる。
相談・訂正・利用終了質問を渡し、回答や訂正理由を記録。必要なら全資料を持ち出す。回答により変わる事実・方法・金額を区別し、元版付きの訂正版を生成。アプリ更新や利用終了後も、採用した資料と計算の根拠を読める。
開発段階は単一の一直線のステータスにしない。「旧版を利用中」「次版を開発中」「一部を外部提供」が同時に成立する。制作物、効用や改良の単位候補、用途別の利用状態、出来事、期間を分ける。図の矢印は代表的な出来事であり、全員が順番に通過する必須ウィザードではない。
P5

お金の全体像と年をまたぐ計算

支払から配分、処理候補、当年費用と翌年残高までを一つの根拠で追跡する。

完成形の必須要件計算・記録の契約避ける誤り
全費用の対応付け契約・請求・購入を一度記録し、複数の制作物・活動・私用等へ分ける。根拠が直接ある費用は直接対応。全費用を一律にトークン割合で割る。制作物ごとに請求を複製する。
利用量の位置付け実契約×対象期間内でProvider固有の定義を検証し、利用量を配賦基準として使う。採用方法と推定を保持。トークンを支払額や業務実態の確定証拠と同一視する。別契約の分母を混ぜる。
複数段階の原価形成設備の当年償却等が制作物原価へ入る場合、基礎額→寄与→残高移動に親子の出典IDを持たせる。設備購入、設備償却、制作物原価への組入れを全部当年費用として足す。
税務単位の実態制作物、資産等の単位候補、改良計画、複数用途の関連を保持。版番号の変更やフォルダ統合とは別に判断。フォルダや金額の都合に合わせた形式的な単位分割。
