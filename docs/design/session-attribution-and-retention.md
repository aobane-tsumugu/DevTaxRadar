# セッション単位の帰属と履歴保全 設計

Date: 2026-08-01
Status: 承認待ち
対象バージョン: v0.1.0 の公開前

## 1. 背景

現状分析で、公開前に解消すべき問題が21件見つかった。うち中核は次の2つである。

第一に、履歴フォルダと制作物の対応が壊れている。ユーザーが明示的に割り当てていないフォルダが、無言で1件目の制作物へ紐づけられる。実測では57個の異なるフォルダが1つの制作物へ集約され、配賦明細131行がすべて同じ名前で表示された。これは「恣意的な資産分割をしない」「税務上の単位はユーザーが確認する」という本製品の中核主張と矛盾する。

第二に、集計が月粒度に丸められており、同じフォルダの性質が月の途中で変わる場合を表現できない。`usage_events` は `session_key` を持つのに発生日時を保存しておらず、`resolveMonthlyProjectMapping` は「月全体を1つのルールが覆う場合だけ採用」する。外れた月は丸ごと未分類へ落ちる。

さらに調査の過程で、製品の前提に関わる事実が判明した。Claude Code は `cleanupPeriodDays`（既定30日）に基づき、**起動のたびに**それより古いセッションファイルを自動削除する。README が掲げる「過去の履歴を整理する」モードは、既定設定のユーザーには30日分しか成立しない。

## 2. スコープ

### 本設計に含む

- 領域1: 税務単位とプロダクト名の手動管理（セッション単位の帰属を含む）
- 領域4: 表示・データ層の是正（分析で列挙したバグ群）
- 履歴保全: 保持期間の検出・警告・承認制の書き換え、取り込み時ハッシュ記録
- セッションの内容確認と resume 支援

### 本設計に含まない（公開後の別サイクル）

- 領域2: 料金モデルの再設計（年プラン、月次プラン、日割、内税）
- 領域3: 領収書の自動取り込み

領域2は現在の「provider ごとに月額1つ」という構造を契約レコードへ置き換える大きな変更であり、領域3は領域2に依存する。公開を待たせる理由がないため分離した。ただし本設計のバグ修正のうち B2（月額0円のまま保存できる）と I1（全月一律適用）は領域2と同じ箇所を触るため、本設計では暫定対応にとどめ、根本解決は領域2で行う（8.3 を参照）。

## 3. 決定事項

| # | 決定 | 理由 |
|---|---|---|
| D1 | 全フォルダを何らかの分類へ割り当てる運用にする | 未割当を残さないというユーザー方針 |
| D2 | 「私用」「一般学習」は制作物ではなく分類ラベルとして持つ | 資産を形成しないものにダミーの制作物を作らせない |
| D3 | ルールはフォルダ×期間で登録し、セッションの発生日時で適用する | 月の途中の切替を未分類にせず表現できる |
| D4 | `usage_events` をセッション単位へ集約して保存する | 集計は常に丸めており、メッセージ粒度を保つ意味がない |
| D5 | 解決ロジックはサーバのメモリ内の純関数とする | 判定が1箇所に集まり単体テストできる |
| D6 | `project_mappings`（legacy）を廃止し planning へ一本化する | プロダクト名の出どころが追えない二重管理を解消する |
| D7 | セッションIDと元ファイルパスをローカル参照として保存する | resume と内容確認に必須。別テーブルへ隔離して漏出経路を塞ぐ |
| D8 | 保持期間は検出・警告し、承認制で書き換える | 気づかないうちに配賦根拠が消えるのを防ぐ |
| D9 | 保持期間の値はユーザーが決める。製品は推奨値を押し付けない | 適切な長さは事業形態・申告方式・ディスク事情で変わる |
| D10 | 月と日付の判定はローカルタイムゾーン基準とする | 税務上の月次記録は日本の暦で行う |

## 4. データモデル

### 4.1 `usage_events` の作り直し

```sql
CREATE TABLE usage_events (
  id INTEGER PRIMARY KEY,
  provider TEXT NOT NULL,
  session_key TEXT NOT NULL,
  project_key TEXT NOT NULL,
  month TEXT NOT NULL,
  started_at TEXT NOT NULL,
  ended_at TEXT NOT NULL,
  message_count INTEGER NOT NULL,
  project_label TEXT,
  model TEXT,
  input_tokens INTEGER NOT NULL DEFAULT 0,
  output_tokens INTEGER NOT NULL DEFAULT 0,
  cache_read_tokens INTEGER NOT NULL DEFAULT 0,
  cache_write_tokens INTEGER NOT NULL DEFAULT 0,
  schema_version TEXT NOT NULL,
  confidence TEXT NOT NULL,
  UNIQUE(provider, session_key, project_key, month)
) STRICT;
```

Adapter はメッセージ単位のイベントを返し続けるが、サーバ側で `(provider, session_key, project_key, month)` に集約してから保存する。実測46,004行が約1,000行になり、DBは15MBから数百KBへ縮む。

`started_at` はそのグループで最も早いメッセージ時刻、`ended_at` は最も遅い時刻。ルール判定には `started_at` を使う。日をまたぐセッションは開始時刻で判定される、という一貫した規則にする。

これにより UNIQUE 制約が本来の意味で機能する。現在のキーは `observed_at` が全行NULLであるために衝突せず、偶然正しく動いている（SQLiteはNULL同士を重複と見なさない）。日時を入れた瞬間に `INSERT OR REPLACE` で同時刻のメッセージが潰れ、トークンが失われる状態だった。

### 4.2 `session_references` の新設

```sql
CREATE TABLE session_references (
  provider TEXT NOT NULL,
  session_key TEXT NOT NULL,
  native_session_id TEXT NOT NULL,
  source_path TEXT NOT NULL,
  working_directory TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  byte_size INTEGER NOT NULL,
  file_mtime TEXT NOT NULL,
  captured_at TEXT NOT NULL,
  PRIMARY KEY(provider, session_key)
) STRICT;
```

`working_directory` は Adapter が読んでいる生の `cwd` である。現在はハッシュ化して `project_key` にし、表示用に最後のフォルダ名だけを `project_label` へ残しているが、resume を実用的にするには元のパスが要る（6.3）。

生のセッションIDと絶対パスを物理的に別テーブルへ隔離する。エクスポート、Markdown出力、ダッシュボードAPIはこのテーブルを参照しない。`scripts/privacy-check.ts` の検査対象にテーブル名と列名を加え、混入をコードレビューではなくスキーマと検査で塞ぐ。

`content_hash` は取り込み時点のファイルのSHA-256。再スキャン時に差分を検出し、「元履歴が取り込み後に変更されている」ことを警告できる。

この記録の限界は明記する。同じユーザー権限で動く以上、ハッシュ自体も書き換え可能であり、第三者に対する改ざん防止にはならない。外部の時刻証明があってはじめて第三者性が生じる。それでも、同一PC内で辻褄の合う記録が継続していることは示せる。

### 4.3 `planning_project_rules` の変更

- `tax_unit_id` を NULL 許容にする（D2）
- `classification` に `general-learning` を追加する。`src/core/types.ts` の `WorkPurpose` には既に存在するのに、ルール側の enum になかった

### 4.4 `project_mappings` の廃止

起動時に一度だけ `planning_project_rules` へ移行し、テーブルを削除する。プロダクト名の正は `planning_tax_units.name` ただ一つになる。v0.1.0 は未公開のため、移行コードは次期リリースで削除してよい。

## 5. セッション解決パイプライン

```
usage_events（セッション行）
  -> resolveSessionAssignment(session, rules)   純関数
  -> (month, provider, taxUnitId|null, classification) へ集約
  -> allocateSubscriptions（既存の配賦不変条件は変更しない）
```

`resolveMonthlyProjectMapping` を削除し、次の純関数へ置き換える。

```ts
type SessionAssignment = {
  taxUnitId: string | null
  classification: ProjectClassification
  ruleId: string | null
}

function resolveSessionAssignment(
  session: Pick<UsageSession, 'projectKey' | 'provider' | 'startedAt'>,
  rules: ProjectRuleRecord[],
): SessionAssignment
```

判定手順は次のとおり。

1. `projectKey` が一致し、`provider` 指定がないか一致するルールを集める
2. `effectiveFrom <= startedAt のローカル日付` かつ（`effectiveTo` がないか `effectiveTo >= 同日付`）で絞る
3. 残りが0件なら未割当（`taxUnitId: null`, `classification: 'unclassified'`, `ruleId: null`）
4. 複数残った場合のタイブレークは決定的に定める
   1. `provider` 指定のあるルールを優先（より具体的）
   2. `effectiveFrom` が新しい方を優先
   3. なお同順なら `id` の昇順

1件目の制作物へ自動的に紐づける現在の挙動（`src/App.tsx:1118`）は削除する。未割当は未割当として集計され、金額は「対象外・要確認」へ流れる。

### 5.1 タイムゾーンの扱い

現在の `monthFromTimestamp`（`src/adapters/jsonl.ts:106`）は、ISO8601文字列の先頭を文字列のまま切り出している。Claude Code の timestamp は UTC（`...T23:50:00.000Z`）で記録されるため、**日本時間8月1日の朝9時前に行った作業が7月へ計上される**。月次配賦は月単位で金額を割り当てるため、月境界のずれは配賦額のずれになる。

本設計では、月と日付の判定を実行環境のローカルタイムゾーン基準へ変更する（D10）。あわせて、判定に使用したタイムゾーン識別子（`Intl.DateTimeFormat().resolvedOptions().timeZone`）をスキャン記録へ保存する。後から「どのタイムゾーンで月を切ったか」を説明できるようにするためで、PCを移動した場合の差異にも気づける。

`resolveSessionAssignment` の日付比較も同じ基準で行う。`startedAt` をローカルタイムの `YYYY-MM-DD` へ変換してから、`effectiveFrom` / `effectiveTo` と文字列比較する。ユーザーが画面で入力する日付はローカルタイムのつもりで入力されるため、これが唯一の一貫した扱いになる。

## 6. 画面構成

### 6.1 新画面「フォルダの割当」

サイドバーの4項目目として追加する。

あわせてオンボーディングのステップ3を軽くする。現在は「履歴からプロダクト候補を入力する」と「AI履歴を作っているものへ結び付ける」の2つの折りたたみを抱え、57件のフォルダを760pxのモーダル内で捌かせようとしている。後者をステップ3から取り除き、「主要な制作物を登録する」ことだけに絞る。ステップ5の完了時に「未割当のフォルダがN件あります。フォルダの割当画面で続きができます」と案内し、割当画面へ導線を出す。

構成要素:

- ヘッダー: 未割当件数／全件数、未割当があるときの警告
- ツールバー: 検索、フィルタ（未割当のみ／全部）、並び替え（利用量順／最終利用順／名前順）
- 一覧: チェックボックス、フォルダ名、セッション数、期間、利用AI、割当先（制作物select）、分類（select）、期間を分けるボタン
- 一括操作: 選択中の複数件を、まとめて制作物または分類へ割り当てる
- 行の展開: そのフォルダのセッション一覧（日時、メッセージ数、モデル、加重トークン、何をしたか、resume）

期間ルールは1フォルダに複数持てる。既定は1件で開始日なし（全期間）。「期間を分ける」で2件目を追加し開始日を指定する。

### 6.2 配賦明細からの編集

「なぜそうなる？」の明細行で制作物と分類を変更できる。明細行は月×フォルダなので、変更は**その月の初日を `effectiveFrom` とするルール**として保存する。「5月分が違う」という意図が「5月1日から変更」という記録になり、期間の起点が曖昧にならない。

### 6.3 セッション詳細

「何をしたか」は `session_references.source_path` から元JSONLをオンデマンドで読み、最初のユーザーメッセージの先頭120文字程度を返す。**DBには保存しない**。本文非保存の原則を維持する。

元ファイルが存在しない場合は「履歴は削除済み・集計値のみ保持」と表示する。`content_hash` が一致しない場合は「取り込み後に変更あり」と表示する。

resume はコマンド文字列をコピーボタンで提供する。アプリからプロセスを起動する経路は作らない。ローカルアプリがブラウザ経由で任意コマンドを実行できる構造は、CSRFで守っても現在のセキュリティ境界と釣り合わない。実行の主導権はユーザーのターミナルに残す。

コマンドは作業ディレクトリへの移動とセットで生成する。resume は元のプロジェクトディレクトリで実行しないと文脈が合わないためである。

```
cd "C:\work\pairs" && claude --resume 01ab...
cd "/home/user/work/pairs" && codex resume 01cd...
```

生成時に次を確認する。

- `working_directory` が存在しない場合（移動・削除された）は `cd` を外し、「作業フォルダが見つかりません」と添える
- パスに引用符が含まれる場合はエスケープする。シェル注入を避けるため、パスは必ず引用で囲む
- 区切りは `&&` を使う。PowerShell 5.1 では動かないため、Windows では「PowerShell 7 以降 / コマンドプロンプト / Git Bash で動作します」と注記する

`cd` 部分だけ、`resume` 部分だけを個別にコピーするボタンも置く。ターミナルが既に目的のディレクトリにいる場合があるためである。

## 7. 履歴保全

### 7.1 検出と表示

`/api/runtime` に保持状況を追加する。

- Claude: `~/.claude/settings.json` の `cleanupPeriodDays`（未設定なら既定30）、履歴の最古日、次に失われる履歴の日付
- Codex: 自動削除の有無（現時点ではなし）、履歴の最古日

画面には「あとN日で最も古い履歴が削除されます」と表示する。あわせて、既定30日のまま使っていた場合は**すでに失われている**こと、延長は早いほど損失が小さいことを伝える。

Codex には現時点で自動削除がない（保持期間設定は openai/codex issue #6015 で要望段階）。将来 retention が入る可能性があるため、検出結果は画面に表示し続ける。

### 7.2 承認制の書き換え

`POST /api/retention`（CSRF保護）で次の順に実行する。

1. `settings.json` を `settings.json.devtax-backup-<timestamp>` へコピーする
2. JSONをパースし、`cleanupPeriodDays` キーだけ差し替えて書き戻す。他の設定は保持する
3. パースできなければ書き換えを中止し、理由を返す

Claude Code 自身も設定ファイルのパースに失敗すると cleanup を停止するため、壊すと二重に厄介になる。画面では変更前後をプレビューし、明示的な承認を取る。

### 7.3 期間はユーザーが決める

製品は推奨値を提示しない（D9）。適切な長さは事業形態、申告方式、ディスクの事情で変わる。数か月で十分な人もいれば、数年残したい人もいる。ここを製品が決めると、根拠のない数字を押し付けることになる。

画面では日数を自由に入力させ、判断材料だけを示す。

**判断材料として示すこと**

- 現在の設定値と、それによって次に失われる履歴の日付
- 帳簿書類の法定保存期間は原則7年（欠損金の繰越がある年は10年）であるという事実。ただしこれは帳簿書類についての定めであり、AI利用履歴そのものに保存義務があるわけではない
- 取り込み後も元履歴には価値があること。DevTax のSQLiteは利用者自身が書き換えられるため、自動生成された元履歴のほうが記録としての性質が強い
- 長期間の保存はディスクを圧迫し、**利用状況によっては2桁GBに達することがある**

利用量は人によって大きく異なるため、製品側で容量を推定して見せることはしない。実際の使用量が知りたいユーザーは、自分のディスクを見れば分かる。

### 8.3 B2 と I1 の暫定対応

領域2で契約レコードへ置き換えるまでの間、次の最小限の対応にとどめる。構造を変えないため、領域2の作業を無駄にしない。

**B2（月額0円のまま保存できる）**: 料金入力欄の初期値を、現在の「`useState(30000)` を DB値0で上書き」から未入力状態へ変える。空欄は `undefined` として保持し、保存時に未入力があれば「AI料金が未入力のため、配賦額は0円になります」と警告して確認を求める。0円での保存自体は許す（無料枠や契約前の月がありうる）が、無自覚に0円で進むことは防ぐ。

**I1（全月一律適用）**: provider ごとに契約期間を**日付で**入力させる。`contract_started_on`（必須にはしない）と `contract_ended_on`（解約済みの場合のみ）を `provider_settings` へ追加する。

```sql
ALTER TABLE provider_settings ADD COLUMN contract_started_on TEXT;
ALTER TABLE provider_settings ADD COLUMN contract_ended_on TEXT;
```

月粒度にしない理由は、本設計がセッションを日時で解決する方針だからである。契約側だけ月粒度にすると非対称になり、実際に不整合が出る。7月18日に契約を開始した場合、月粒度では「7月は契約していた／していない」の二択しかなく、7月1日から17日までの利用（契約前なので別の支払いか無料枠にあたる）まで7月の月額へ含めて配賦してしまう。

終了日も持つ。開始日だけでは、解約後の月にも月額が適用され続ける。

適用規則は次のとおり。

- 契約期間と重ならない暦月には、その provider の月額を適用しない（配賦対象の月から外す）
- 契約期間外の `startedAt` を持つセッションは、配賦の分母から除外する。ただし明細には「契約期間外」として金額0で表示する。表示から消すと「なぜこの利用が計上されていないのか」を説明できなくなる
- 日付の比較は 5.1 と同じローカルタイム基準で行う
- 開始日・終了日が空欄のうちは現在の挙動（履歴のある全月へ適用）を維持しつつ、「契約期間が未入力のため、履歴のある全月に同額を適用しています」と警告する

**日割りは行わない**。契約開始月・解約月の月額は満額として扱い、その月の契約期間内セッションへ配賦する。日割り、年プラン、内税、アップグレードは領域2で扱う。ここで近似が残ることは画面に明記する。

月ごとのトグルを置く案は退けた。入力が月数ぶん増えるうえ、領域2で契約レコードへ置き換える際に丸ごと作り直しになる。契約期間を日付で持てば入力は2つで済み、領域2の契約レコードが持つ開始日・終了日へそのまま移行できる。契約の中断と再開（同じ provider を解約して再契約する）は1組の日付で表現できないが、これは領域2で複数の契約レコードとして扱う。

## 10. テスト方針

新規の単体テスト:

- `resolveSessionAssignment`: 該当なし、単一該当、期間の境界（開始日当日、終了日当日）、provider指定の優先、`effectiveFrom` の新しい方の優先、id昇順の決定性
- セッション集約: メッセージ列からセッション行への畳み込み、月をまたぐセッションの分割、`started_at`/`ended_at`/`message_count` の正しさ
- タイムゾーン: UTC表記の `2026-07-31T23:50:00.000Z` が JST 環境で `2026-08` に帰属すること、ローカル日付が `2026-08-01` になること、`effectiveFrom: 2026-08-01` のルールに一致すること。テストは `TZ=Asia/Tokyo` と `TZ=UTC` の両方で実行し、環境依存を明示的に検査する
- 契約期間: 開始日当日のセッションが配賦対象に入ること、開始日前日のセッションが分母から外れて明細に金額0で残ること、終了日当日が対象に入ること、契約期間と重ならない月に月額が適用されないこと、開始日・終了日が空欄のとき全月へ適用されること
- 保持期間: `cleanupPeriodDays` 未設定時に30を返すこと、パース不能時に書き換えを中止すること、他キーが保持されること
- ハッシュ: 取り込み時と再スキャン時で内容が変わった場合に差分を検出すること

## 11. プライバシー方針の改定

D7 により SECURITY.md の記述を改める必要がある。

現在の記述「元のセッションID、メッセージIDを保存しない」「元の絶対パスを保存しない」は、次のように改める。
