## 1. 目的と正本

[全体設計図](workflow-blueprint.html)のP1〜P6・R1〜R6を起点とし、[製品仕様v0.5](../../PRODUCT_SPEC.md)と[技術設計v0.5](../../TECHNICAL_DESIGN.md)の完成像を維持する。本書は実装順序・削除条件の正本であり、新しい製品仕様や別の進捗管理システムではない。要件ごとの現在地と受入は[要件対応表](requirements-matrix.md)、実行結果は[検証証跡](../evidence/v05-revision/CURRENT.md)で管理する。

> 支払・購入 → 期間別の費用基礎 → 制作物・活動への配賦 → 事実に対応する処理候補 → 当年費用候補と残高 → 採用版と翌期首

AI費用だけへ範囲を戻さない。全費用、稼働版と改良計画、判断・相談、年度残高、訂正・繰越を残す。一方、同じ値を別々に作る計算、同じ記録を別々に書く保存経路、仮の数値表示、全員への一律確認を減らす。利用者には事実と例外を確認してもらい、同額の転記や内部IDの手入力を重ねて要求しない。

React・Fastify・SQLite、既存の共通費用projection・保存・採用版・復元を継続利用する。クラウド同期、外部LLMによる判断、全面的イベントソーシング、汎用承認基盤、専用LAN受信や各PC常駐クライアントは導入しない。実装順序はMVPへの範囲縮小や期限ではない。

### W01 保存経路と容量

根拠: 初回レビューF02・F03。対応: REQ-UX-02 / AC-SAVE。

主な対象は`src/server/index.ts`、`workspaceRepository.ts`、`planningRepository.ts`、`configurationSchema.ts`、`src/client/api.ts`と既存API試験。

2026-09-09時点の部分実装の履歴（親commit `7cba579`。現HEADの状態ではない）: workspaceのpreview・saveだけに、共通の2MiB（2,097,152バイト、UTF-8のJSON全体）上限と413の説明を設定した。全体の既定64KiB、残高保存2MiB、年度採用16KiB、復元の専用境界は変更していない。実APIを起動する回帰試験を追加したが、依存関係を取得できない実行環境のため未実行。詳細は[部分実装の記録](../evidence/v05-revision/2026-09-09-workspace-capacity.md)。W01完了・AC-SAVE合格ではない。

同日時点の監査では、`workspaceAttempt.ts`が保存元と要求の両方をJSON化し、2,000,000 UTF-16コード単位を超える控えをHTTP送信前に拒否することを確認した。ブラウザの保存容量不足も別に扱う必要がある。HTTPの2MiBを画面から必ず保存できる保証とはしない。入力を黙って捨てず、控えを必須にしたまま利用者を行き止まりにしない保存・復旧手順を同じW01で整合させる。

- 旧`PUT /api/planning`、`PUT /api/planning/rules`、`POST /api/config`の全呼出し元を調べ、版照合・一括保存のworkspaceへ移す。互換書込が実際に必要な場合だけ、同じ期待版と共通保存へ委譲する。独立した保存ロジックは残さない。
- preview・save等、全体snapshotを受ける入口の容量を揃える。計画時点の64KiBと入力スキーマの不整合を解消し、妥当な上限・UTF-8バイト数・超過時の入力保持を明示する。無制限化や差分同期基盤への全面移行はしない。
- 旧DB・旧採用資料の読取りと移行は維持する。内部保存関数はHTTP経路の削除だけを理由に消さない。残高専用の保存境界をworkspaceへ無理に合体させない。

完了条件: 古いタブとすべての公開書込経路から、新しい保存を無検知で上書きできない。途中失敗はrollbackし、同じ要求の再送は二重書込しない。日本語メモを含む大きいworkspaceをpreview→保存→再読込でき、上限超過では既存データと編集中入力が残る。64KiBを超える合成例と採用した上限の前後を実APIで検証する。

### W02 取得条件と数値記録の保全

根拠: 追加監査A1・A2・A3。対応: REQ-SOURCE-01/02、REQ-COST-04、REQ-RECORD-02、REQ-RESTORE-01 / AC-TIME、AC-SOURCE、AC-RECORD、AC-RESTORE。

- 月・期間の区切りに使う時間帯を計算条件へ含める。キャッシュの同一性・再正規化・復元後の再走査を揃え、走査表示の時間帯だけ新しくなる状態をなくす。採用済みの帰属は変更しない。
- 数値寄与に、取得元・対象期間・方式版・前回値使用・未取得または範囲不明を結び付ける。走査完了と利用の完全捕捉を区別し、採用資料・出力まで来歴を残す。保留件数だけから影響額を推定しない。
- 年度採用前の保全は、先に「自動走査で観測が置換される前のどの時点に、何を残すか」を既存保存機構に沿って決める。未判断でも数値と計算条件を保全できるようにし、手動backupや年度採用を先に済ませたという仮定に依存しない。現在の観測cacheを全文永久保管庫へ変えない。
- 不安定・形式不適合はファイル単位の保留を維持する。root・列挙・読取I/O失敗等の取得元全体の保護と混同しない。他の正常な対象を一律停止しない。

完了条件: UTCで取得→日本時間で再起動→変更あり・なしのファイルを混在させて増分取得しても月が混ざらない。旧値使用と初回未取得を再起動・採用・Markdown/JSON後も区別できる。夏に取得→未判断・年度未採用→元履歴消失→自動再走査の後も、保全した数値と条件を説明できる。原本なしの数値記録を原本や法定保存の代替と表示しない。

### W03 契約・期間別の配賦

根拠: 初回F01・F07、追加B1・B2。対応: REQ-EXPENSE-01、REQ-SOURCE-02、REQ-COST-02/03/04 / AC-EXPENSE、AC-ALLOC、AC-CAPTURE、AC-TIME、AC-SOURCE。

主な対象は`src/core/chargePeriods.ts`、`allocation.ts`、`src/server/dashboard.ts`、`src/adapters/codex.ts`、請求・取得元の設定と入力。

- provider・実契約・履歴取得元を別の概念として扱う。通常の1サービス1契約は既定生成する。複数契約の場合だけ、履歴と適用期間を対応付ける。sourceに複数契約が混ざる場合も考慮し、source全体を一契約と決め付けない。

- Codexの長期会話は、実際に取得できる時点別の情報で分割できる範囲を検証する。累積リセット・重複を扱い、取得粒度を超えた月割りや用途帰属を作らない。別PCの同一IDの分離と、同一実履歴の複製候補の検出を区別する。native ID一致だけの自動削除をしない。

完了条件: 同サービス・同期間の契約A8,000円/制作物Aと契約B2,000円/制作物Bは8,000円・2,000円になる。単一契約の既存結果を変えない。対応不明、月途中、年越し、捕捉不明、複製候補を含めても原額を失わず二重配賦しない。長期会話は精度の限界を表示する。
